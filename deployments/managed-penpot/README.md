## Smallest topology

Keep the existing Google-authenticated Cloud Run Studio, named Firestore database, GCS assets and Cloud Tasks exactly as they are. Add one costed `e2-standard-2` (2 vCPU, 8 GiB, x86_64) running this private Compose stack. Only the TLS gateway publishes 80/443. Native backend, exporter, Postgres, Valkey and the proof adapter have no host ports. The frontend, backend, exporter and database use the `native` internal network; only TLS and the fixed-purpose adapter also join `edge`. Adapter egress goes to the configured Studio HTTPS origin; it is not a general relay. No managed SQL/Redis, external load balancer, NAT, second VM, Doory frame/model or paid inference service is added.

The committed template uses service names `penpot-frontend:8080`, `penpot-backend:6060`, `penpot-exporter:6061`, `penpot-postgres:5432`, `penpot-valkey:6379` and `studio-native-connect:39044`. The native hook's private `callbackOrigin` is exactly `http://studio-native-connect:39044`. The managed Studio config's `rpcOrigin` must be reachable from Cloud Run: normally the exact **public HTTPS native gateway origin**, not the VM-only Docker hostname. The same config mounted on the VM adapter may use that HTTPS origin too. Internal RPC can instead be used only after actual existing private Cloud Run-to-VM connectivity is supplied; none is assumed or provisioned. The constructor keeps RPC origin separate from browser links even when both use the same HTTPS value.

`PENPOT_PUBLIC_URI`, the managed config's `nativeOrigin`, the first-party gateway's accepted Origin, TLS hostname and native public-cookie configuration must agree. Google remains Studio's normal identity provider. Native profile proof reads the actually signed-in native account; existing pairing, immutable workspace registration and current brand grants remain in use. No password developer launcher or automatic account creation is exposed. Native login may use its existing native credentials; this does not change Studio Google sign-in.

## Storage, capacity and budget

Use explicit persistent data storage, not container writable layers: Postgres `database`, native `assets`, TLS certificates/config. A VM boot disk can hold Docker metadata; the data disk must be mounted at the reviewed Docker-volume root or explicit bind source before volume creation. Do not let an unmounted data disk silently create fresh root-disk data. Proposed bounds reuse observed native caps: backend 2 GiB, exporter 1 GiB, frontend 384 MiB, Postgres 384 MiB, Valkey 192 MiB, plus TLS 128 MiB and adapter 128 MiB (about **4.19 GiB** total caps). Studio remains Cloud Run, not in this VM. CPU quotas are per-service scheduling ceilings and oversubscribe the 2-vCPU host; exports run serially for two-user pilot use. These are planned limits, not a concurrent peak benchmark.
