# Private studio backend

The running application selects organization and brand on each authenticated request. Query parameters `organizationId` and `brandId` (or equivalent `X-Organization-Id` / `X-Brand-Id` headers) select a scope only after explicit membership validation. There is no global active tenant. Studio routes require membership; admin routes also require founder role. Scoped state includes drafts, profile/calendar, jobs, telemetry, usage, preflight evidence, and downloadable assets. Preset IDs describe content and never grant access.

## Local identity and persistence

Use Node 22. Set `STUDIO_DATABASE_PATH=/data/studio.sqlite` on a persistent volume writable by the container user. Default storage mode is sqlite. The database uses WAL, a five-second busy timeout, schema version 1, and `BEGIN IMMEDIATE` for atomic mutations. Independent edits read the current document within the transaction; revision checks reject stale saves with 409. Generation also checks that the story did not change while a provider request was in flight.

Initial provisioning reads `STUDIO_FOUNDER_USERNAME` (default founder), `STUDIO_FOUNDER_PASSWORD`, `STUDIO_MARKETER_USERNAME` (default marketer), and `STUDIO_MARKETER_PASSWORD`. Passwords require at least 12 characters; there are no built-in passwords. Configure both accounts before the first demonstration. Account setup grants explicit membership in the initial Studio organization and both brand scopes. Additional organizations and brands require founder actions. Accounts and salted scrypt hashes persist independently of environment variables. Changing a bootstrap environment password does not silently reset an existing account.

`POST /api/auth/login` accepts username/password and sets an eight-hour HttpOnly SameSite=Strict cookie. `GET /api/auth/session` returns user, organizations/brands, activeScope and permissions; an unsigned request returns 401 with user null. `POST /api/auth/logout` revokes its session. Password failures are throttled after ten attempts per username per fifteen minutes. Set `STUDIO_COOKIE_SECURE=true` behind the trusted HTTPS Cloud Run endpoint; HTTPS same-origin checks use this explicit setting and never trust arbitrary forwarded headers. Optional `STUDIO_ALLOWED_ORIGINS` is an exact comma-separated allowlist; wildcard CORS is absent.

Founder account management: `GET /api/admin/users` lists public user IDs within the selected organization. `POST /api/admin/users/:id/password` accepts `{ "password": "a new secret supplied securely" }` in the selected scope and rotates that account's scrypt salt/hash while revoking every older session through a durable authentication version. Never put real passwords in issue bodies, examples, or shell history. User IDs outside the founder's selected organization are rejected.

## API data and assets

Existing studio bootstrap, profile, backlog, schedule, generate, save-edit and export routes require scope. Backlog/source-claims accept sourceClaims with explicit kind (`financial`, `cultural`, `clinical`, `general`), HTTPS sourceUrl, text, ID, and review status. Discovery and legacy seeds remain unreviewed. Approval is an authenticated editorial act, not automated factual verification. Clinical claims additionally require explicit founder-recorded source review through `clinicalReviewRequested:true`; the server stamps reviewer identity/time and ignores client-supplied reviewer IDs. Changing the claim text/source invalidates the previous review.

Save-edit accepts `expectedRevision` and returns the updated story. Source-claims and preflight accept the same revision check. Preflight recomputes checks from raw canvas/text geometry, colors and caption using the shared pure function; stored evidence binds revision, generation, settings and time. Its result is a simulation and never a confidence score. Generated campaigns and exports retain generation lineage.

Export reads the saved campaign, renders a real PNG (infographic/story), four-PNG ZIP (carousel), or text script (reel), then persists the artifact before marking its revision exported. `GET /api/studio/assets/:id` independently authorizes the selected scope. Output uses an attachment filename and exact content type. No publishing or video rendering is claimed. Admin overview exposes real job history, failed/synthetic generation counts, client simulation evidence, and sanitized operational errors. The source-excerpt score explicitly does not assess factual or clinical accuracy.

## Discovery and weekly jobs

`POST /api/studio/ingest` accepts a curated JSON `{items:[{sourceId,title,sourceClaims}]}` feed. Every incoming claim becomes unreviewed regardless of its supplied status; sourceId is deduplicated within the brand. `POST /api/admin/discovery-config` stores a feedUrl only from exact HTTPS hosts configured in `STUDIO_DISCOVERY_HOSTS`. Fetches are bounded to five seconds and one MiB, reject redirects/private IP resolution, and pin the validated DNS address. This is configured curated discovery, not an unrestricted social-media crawler.

Manual founder batches use `POST /api/admin/run-weekly-batch` with `idempotencyKey` and maxStories (1–50). Stages persist discovery, eligibility/review filtering, formatting and outcomes. Repeated keys replay the durable result; overlapping different keys receive 409. A thirty-minute lease marks crashed runs interrupted before a later distinct run can proceed. Failed runs preserve completed/failed story IDs and successful generation IDs. An explicit retry supplies a new idempotencyKey plus retryOfJobId referencing a failed/interrupted job in the same brand; each attempt records parent/root job IDs, its attempt number and inherited completed story IDs. Retries skip previously completed stories even if their saved draft is later removed. Reusing a key with different retry lineage is rejected. There is no claim that unreviewed discovered content is automatically publishable.

For Cloud Run Jobs use `node server/run-weekly-batch.js` with explicit `STUDIO_JOB_ORGANIZATION_ID`, `STUDIO_JOB_BRAND_ID`, `STUDIO_JOB_MAX_STORIES` (1–20), and optional `STUDIO_JOB_IDEMPOTENCY_KEY`. An operator retry also sets `STUDIO_JOB_RETRY_OF_JOB_ID` with a distinct idempotency key. Default keys identify the Monday of the current America/New_York week. The job verifies its configured scope exists, writes a named service-actor result, closes storage, and exits nonzero on failed/interrupted/incomplete work. IAM controls who may invoke the job; this does not pretend HTTP Scheduler bypasses application authentication or IAP.

An optional direct scheduled HTTP route `/api/internal/scheduled-batch` verifies Google RS256 identity signatures, issuer, service-account email (`STUDIO_SCHEDULER_EMAIL`), audience (`STUDIO_SCHEDULER_AUDIENCE`), expiry and explicit allowed scope pairs (`STUDIO_SCHEDULER_SCOPES` JSON). It derives an idempotency key from the supplied key or Scheduler schedule-time header after identity verification. No deployed Scheduler or cloud resource is implied by implementing that route.

Generation attempts reserve durable UTC-day slots before a provider call: `STUDIO_DAILY_GENERATION_LIMIT` defaults to 20 per organization, and `STUDIO_GLOBAL_DAILY_GENERATION_LIMIT` defaults to 20 for the installation. The installation counter is shared by every organization and brand using the same backing store/database and Firestore collection; it is not a per-brand allowance or a cap across independent installations. Failure and synthetic outcomes remain distinct usage events. Reservations are conservative and are not refunded on ambiguous crashes or quota races. These are attempt caps, not measured dollar billing; they do not prove a $100 monthly ceiling for arbitrary models. Configure provider quotas and reviewed budget alerts separately before paid cloud use.

## Backup, recovery and customer exit

For local snapshots: `node server/storage-admin.js backup /data/studio.sqlite /secure/backup.sqlite`. The destination must not exist. SQLite produces a consistent standalone snapshot, including accounts and sessions; protect it as a secret. To restore, stop this application's container, preserve its entire existing data directory, then `node server/storage-admin.js restore /secure/backup.sqlite /fresh/data/studio.sqlite`. Restore validates SQLite integrity, schema and JSON records, refuses overwrite, and creates a private file and revokes all restored sessions. Passwords revert to the snapshot values; rotate them through the explicit account endpoint after recovery. Point the service to the restored path and verify both accounts and drafts. Never copy a live WAL database file alone or replace it while a process is writing. Reverting application code does not migrate a newer schema backwards; startup rejects a newer schema version.

Founder `GET /api/admin/eject` returns only the selected brand's self-contained schema-versioned JSON manifest, organization/brand IDs, data checksum, and actual artifact bytes/checksums. Accounts, sessions, global quotas and credentials are excluded. Cloud objects are downloaded into the package; raw managed-bucket references are stripped. `POST /api/admin/import` restores a verified package; different destination scope requires `{bundle: PACKAGE, remapScope:true}`. Imports reject malformed schema, mixed-scope records, orphan assets and checksum failures. This is the customer exit route, not an account/session backup. Back up the destination before replacing its content; rollback restores that prior package into the same scope.

Admin `/backprop-jsonl` exports every feedback record, beyond the 25-row display window, including stable generation IDs, baseline/final content and preceding edit content. Every row has an explicit eventType and preferenceLabel:null: generation baselines, human edits, schedules, downloads and other operational events are not preference labels. Legacy events are classified on export without changing their raw generation baseline. There is no automatic training or optimization step. Export and download boundaries are scoped again on each request. Firestore/GCS deployment requirements and explicit four-MiB per-record capacity limits are documented in firestore-gcs-storage.md. Cloud readiness checks both store and bucket; provider connectivity remains not_checked.

## Verification

Run `node --test server/*.test.js` from liquidity-studio. Platform integration covers both roles, all scoped route denials, durable drafts/real downloads, complete feedback export, optimistic conflicts, conservative quotas, asynchronous storage, broken dependency/error persistence, HTTPS origins and bounded readiness. Contract scripts use named synthetic source fixtures with explicit trustedTestMode injection; production startup has no test bypass. The existing port-3000 process is outside this implementation's deployment scope.

### Public Cloud Run health paths

Use `GET /api/live` for process liveness and `GET /api/ready` for repository readiness when monitoring the public Cloud Run URL. Cloud Run [reserves some paths ending in `z` and recommends avoiding them](https://docs.cloud.google.com/run/docs/known-issues#reserved_url_paths); the deployed `/healthz` was intercepted with404 even while the application was reachable. Existing `/healthz` and `/readyz` paths remain compatible for internal/container probes.

Both aliases are intentionally anonymous and return the same minimal JSON as their existing counterparts. Liveness does not wait for startup/storage. Readiness keeps its bounded repository check and reports generation provider `not_checked`; it does not prove paid inference, user login or full artifact delivery. A failed dependency returns503 without its exception text. Protected session and workspace APIs still require authentication and return401 anonymously. This change needs no data migration; rollback removes only the new aliases, so update external monitors before reverting.
