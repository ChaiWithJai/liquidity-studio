# Firestore maintained-source follow-through proposal

Source review only, 2026-10-18. Baseline `7c08a61` (merged PR181). No cloud access, application execution, local tests or maintained writes occurred. This proposes an internal operator implementation; it does not extend the SQLite command to Firestore by removing its type check.

## Existing seam and gap

`server/seed-followthrough-apply.js:17` requires the same actual DurableStore connection. Its synchronous `currentPlan` reads identity and all logical keys while SQLite holds BEGIN IMMEDIATE. `server/cloud-store.js:66` already has multi-key transactions, but these accept only named records. `keys()` at line110 runs an independent, unbounded query outside a transaction. Calling that before `transact()` leaves both stale inventory and a new-key phantom window. Calling async SDK reads inside the existing synchronous workspace/job guard is also incorrect.

`server/repository.js:68` wraps `store.update()` with restore-lock and monotonic content-epoch handling. WorkspaceService.mutate (`workspace.js:199`) and OperatorJobService.create (`operator-jobs.js:352`) already invoke trusted control guards inside that update, with receipt binding. Preserve those semantic operations, their idempotency, and the separate title and queue transactions. No repository replacement, source approval, unrestricted ingestion bootstrap, worker invocation, or quota reset is needed.

## Minimal implementation

1. Add an explicitly bounded store primitive, proposed `FirestoreStore.transactWithKeyInventory(keys, callback)`. Reuse `transactionKeys` (1–8 unique bounded keys), `read()` checksum/chunk verification, `transactionValues` (aggregate next values ≤4MiB), unchanged digest/no-op logic and maxAttempts5. No general HTTP endpoint.
2. Inside the SAME read-write Firestore transaction, before any writes, query the parent collection with `orderBy('key').select('key').limit(513)` through **transaction.get(query)**. At most512 logical parents are admitted. This is an operator-admission bound, not a lower product/store capacity. If513 arrive, fail closed without scanning/paging or writing. Use no collection-group query, GCS listing, external storage download or new index infrastructure.
3. For fail-closed malformed-record coverage, issue a second bounded parent query ordered by document ID, selecting key, also limit513. Compare exact parent-ID/key pairs against the key-index query, require each key valid under existing512-byte rule, unique, and document ID equal SHA256(key). This catches a parent lacking a key (which an orderBy-key query otherwise omits), invalid mapping or inconsistent inventory. No chunks are included in these parent queries. All production store parent writes already carry key; subcollections are excluded naturally.
4. Read identity and selected scope plus their chunks through existing `read(transaction,...)`. Perform both inventory queries and all chunk reads before calling a pure synchronous callback or staging any writes. Limit total observed key UTF8 bytes to512×512=262144; query snapshots contain only ID/key, not record payloads. Existing selected-value 4MiB aggregate write limit remains unchanged; additionally reject aggregate decoded current identity+scope JSON above4MiB before invoking the guard. Existing individual records can each approach4MiB, so read-side transient memory can exceed4MiB; this is not a maximum-memory proof. Do not decode unrelated logical values.
5. Build a PRIVATE per-invocation operator store facade, never patch a shared production instance. Its `update()` accepts only the selected scope key and delegates to the primitive with `[identity, scopeKey]`. Within its synchronous update callback expose a transaction snapshot view containing detached identity and the exact key inventory to the existing pure plan/row guards. Its ordinary get/read delegates normally; no synchronous network methods or globals. Extract a small common follow-through algorithm taking an explicit transaction-view accessor, retaining the SQLite implementation/type guard as-is. Reuse ScopedRepository.restore/contentRevision wrapper and existing Workspace/Job services, not duplicate their mutation logic. Construct only against an existing reviewed scope, refuse absent scope rather than allowing constructor initialization to seed it.
6. Title and job phases each get a fresh transactional identity/inventory. The existing immutable post-title receipt stores exact content epochs/story hashes/input fingerprints. The job phase must recheck that receipt and scope-state hash, current founder/membership/preset, catalog/source hashes and empty scoped external inventory before queue creation. Replay remains original actor/key/request binding; an intervening change can leave an accepted title receipt but must prevent fresh job creation. Never substitute a later revision.

## Inventory semantics and concurrency

Filter the complete admitted logical inventory with the SAME SQLite rule: exclude the selected scope key; include a key containing `:${organizationId}:${brandId}:` OR ending `:${organizationId}:${brandId}`. This retains unknown namespace detection and avoids a brittle prefix allowlist. Unrelated scopes remain excluded from eligibility, although their parent records count toward the conservative512 admission limit and can cause harmless transaction retries.

A list captured outside the transaction is not sufficient. Firestore read-write query transactions are intended to serialize query observations with writes; the specific empty-range/new-document behavior must be proved with the real hosted emulator, not a fake store that serializes callbacks. Do not implement a client-side second query as a purported atomic fix. If a committed concurrent matching insertion can escape the transactional query guard, HOLD implementation and revisit a universal scoped inventory epoch across writers; do not claim the current primitive is safe. That broader epoch would touch every writer and is not this minimal proposal.

Logical serialization matters: a native write ordered AFTER the title operation is not retroactively forbidden. The second queue transaction must then see it and refuse work. A writer ordered before the guarded operation must be reflected or force retry. Current identity revocation, scope changes and unknown external records receive the same treatment. Out-of-band raw Firestore writes violating the store schema are unsupported; the second parent query detects the bounded missing-key case rather than silently treating it as empty.

## Hosted checks required before operations

Extend the existing real loopback Firestore emulator contract suite (`server/cloud-store.emulator.test.js`), with two independent SDK clients and unique test collections. No local runner is proposed.

- Current identity and scope are read in one transaction; held writer changes membership, title, content epoch or restore lock. The semantic operation retries/rejects and preserves the newer work, without a job.
- Hold a queried transaction before its first write; another client inserts a previously absent matching native/review key. Assert valid serial ordering: either guarded operation commits before the insert or query retries and detects it. A previously committed matching insert must never be missed. Use SDK retry/commit barriers without assuming pessimistic locks permit a writer to complete while held.
- Repeat empty-range insertion in a new unknown namespace and exact-suffix key. Repeat unrelated-scope insertion: eligibility unaffected, retry allowed. Test deletion/update of an observed parent and a malformed missing-key parent.
- Assert all query/chunk reads precede writes, retry callback has no external side effects, failed guard writes nothing, unchanged identity is not rewritten, and contentRevision advances only for actual title changes.
- Exactly512 parents succeeds;513 fails before callback/writes. Invalid/duplicate/mismatched keys, >512-byte key, current aggregate capacity and next aggregate4MiB limits reject. Bound query cardinality and prove no artifact downloader is called.
- Full real Workspace/Job composition: fresh exact registry plan → semantic title receipt → fixed reviewed source job. Hold an ordinary human edit between phases; titles remain, queue refuses. Lost-response retry uses identical title/job keys and makes no duplicate job/reservation. Wrong actor/source commit/plan hash and payload conflict deny. Four reviewed IDs only; no source approval fabricated.

Hosted fake SDK tests can additionally verify query limits/order/projections and all-read-before-write behavior, but cannot substitute for the phantom/concurrency emulator cases. Actual maintained GCP follow-through still requires a current asset-aware backup, fresh reviewed read-only plan and exact deployment/source binding, explicit operational handoff and bounded Neo observation. No such operation is authorized or performed by this proposal.

## Operational bounds and cost

One phase reads at most two513-parent projected query snapshots, plus identity/scope parent/chunks (each up to33 chunks under128000-byte chunking). A successful two-phase attempt therefore has nonzero Firestore document-read cost; retries can multiply it up to five attempts. This is deliberately a one-off operator path, not bootstrap-per-request behavior. No new services, IAM, bucket, collection, dispatcher or paid model calls are introduced. Failures do not widen the query limit automatically. Query/SDK deadlines and transaction retry ceilings must be explicit in the eventual operator entry; an HTTP timeout alone does not cancel SDK work. Exact hosted SDK transaction options should be verified against the installed version before implementation.
