## Actual setup

A separate disposable checkout built the upstream backend Dockerfile without Chromium. Production Django settings retained authentication and CSRF; only the local HTTP cookie/redirect configuration and trusted local frontend origin were selected. API and realtime ports bound exclusively to loopback 39007/39009. Postgres and Redis had no published ports. One API worker and one realtime worker ran in an isolated Compose network, with memory caps 384MiB database, 128MiB Redis, 768MiB API and 512MiB realtime. Observed idle usage was approximately 212MiB across the four containers; this is not a load-test capacity result.

All font, element, model and audio sync flags and template seeding were false. Migrations ran, including upstream built-in preset migrations. No external assets or model weights were seeded. The first harness startup failed because its email URL used an unsupported `dummy` scheme; changing the disposable configuration to `memorymail://` allowed startup without outbound email. This was a harness configuration correction, not a patched upstream runtime.

Backend dependencies have ranges rather than a frozen Python lock. The actual local image was ARM64, image ID `sha256:00449a7f40d7ec43ecd3cff969e375989ae25419a573ff302bdeff6bcaf7fe8c`; Python 3.14-slim base manifest `sha256:a2b82f3c48559aa0a8446d9af49826b6e2b2016f4cd2afabfe6013ec53729170`. Postgres 16-alpine manifest `sha256:57c72fd2a128e416c7fcc499958864df5301e940bca0a56f58fddf30ffc07777`; Redis 7.2-alpine manifest `sha256:29e8589c3f9ba699b5f7aa4b3c7733c58852a3626439e619aa0ee78de08c6ca0`. ## Actual HTTP and WebSocket checks

The [reproduction harness](../../scripts/investigations/doory-native-acceptance.py) uses two ephemeral QA owners, actual CSRF/session login and a [two-page native JSON fixture](../../scripts/investigations/doory-native-fixture.json). Credentials remain outside the repository; no browser automation was used by this harness. [Sanitized results](39-doory-native-api-evidence.json) record the checks and document hash.

- Create and GET preserved the complete two-page schema-v1 JSON exactly. PATCH changed a native textbox heading; GET preserved that change. A stale `base_revision` returned 409.
- The second owner received 404 for the first owner's GET and PATCH. Login without a CSRF token returned 403.
- A valid public view-share intentionally exposed the document to an anonymous GET. This is upstream sharing behavior, not Studio brand authorization. A signed-in view-share writer received 403. A password-protected share returned 401 until the correct password was supplied.
- An anonymous collaboration socket closed 4401; an authenticated outsider supplying an invalid share token closed 4403. A valid view-share joined with `canWrite:false`. Disabling that share closed the already joined socket; this single Redis-backed observation took 0.01 seconds after the revocation call. Revoked anonymous HTTP GET then returned 404. This is not a universal revocation-latency guarantee or multi-replica load test.
- An explicit controlled copy of the exported document JSON created a new design under the second QA owner, preserved exact JSON and rejected the original owner's GET. The original design was retained. This proves a native JSON API copy with explicit owner mapping, not delete-and-restore acceptance or a self-contained portable archive.

Doory's owner model has no Studio organization/brand membership semantics. Calling these two QA owners “two brands” would overstate the result. Font bytes, asset rewriting, attribution inventory, identity mapping, browser-native hydration, backup recovery and cross-editor conversion need separate evidence. No Penpot import, Studio adapter, clinical correctness or background-removal inference is established by these checks. Issue 39 remains open.

## Reproduction controls

The [isolated Compose configuration](../../scripts/investigations/doory-native-local.compose.yml) requires `DOORY_SOURCE_DIR` pointing to the pinned disposable checkout and a private env file containing random `POSTGRES_PASSWORD` and `DJANGO_SECRET_KEY`. Do not print the resolved Compose configuration because it includes credentials. Build only this backend, start only the named project, wait for migrations, and create two ephemeral users `owner-a@example.invalid`/`owner-b@example.invalid` with a shared random test password, verified flags and no personal credentials. The harness reads that password from `QA_PASSWORD` in `private.env` under an explicitly selected `DOORY_EVIDENCE_DIR`; use an existing Python environment with requests and websockets installed. It writes reports and native JSON only into that selected evidence directory.

Run `DOORY_EVIDENCE_DIR=/your/private/evidence python3 scripts/investigations/doory-native-acceptance.py` against the disposable local services. The fixture is original text only. Do not target production, change Studio allowlists or use real user accounts. Repeated runs create new designs/shares and require the ephemeral users to exist. The browser preview uses the separately built pinned frontend, API proxy 39007 and WebSocket proxy 39009; frontend origin 39006 is explicitly trusted for CSRF. Cleanup only this experiment's containers/network/volumes after preserving evidence and completing the operator browser check.
