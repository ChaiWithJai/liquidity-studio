# Browser-local assistant feasibility for the collaborative Studio

Research checkpoint 2026-10-18 UTC; no model weights downloaded, no inference run, no new service/cloud account or device purchased. Public model metadata, cards and runtime source were inspected read-only. [Pinned metadata](39-browser-model-metadata.json) records revisions, selected file sizes and inspected source hashes. This extends issue #39's operator/human-AI requirements; it does not replace the 70-item pipeline ledger or claim a local assistant exists. The separate UX/annotation atlas and iterative review plan retain the filesystem review corpus as evidence. This paper addresses model feasibility only.

Recommendation: first build a narrow typed application action surface and deterministic baseline. Then compare Bonsai 2B text planning over semantic workspace state with optional vision assistance. Give each authorized human their own local inference session; keep the shared authorized workspace authoritative on the server. Do not select a robot model or buy Jetson/Nebius capacity from parameter count or a demo speed.

## Nebius and NVIDIA evidence: related domains, different action spaces

[Nebius's March 16 physical-AI announcement](https://nebius.com/newsroom/nebius-teams-with-nvidia-to-build-cloud-for-robotics-and-physical-ai) describes infrastructure, simulation, training and deployment with NVIDIA. Its [PhAIL announcement](https://nebius.com/blog/posts/nebius-partners-with-positronic-on-physical-ai-leaderboard) describes physical bin-picking evaluation using throughput/reliability. Neither identifies a particular tiny browser UI model. The user's specific “tiny robot VLM” reference remains unresolved; do not invent a Nebius checkpoint or convert cloud-infrastructure marketing into local-model compatibility. No Nebius service was called or priced as a selected deployment.

[NVIDIA Cosmos-Reason2-2B](https://huggingface.co/nvidia/Cosmos-Reason2-2B) is a physical-world reasoning VLM. Its public metadata lists a 4,877,470,304 byte model tensor artifact; raw card download was gated in this unauthenticated inspection. The public card identifies the [NVIDIA Open Model License](https://www.nvidia.com/en-us/agreements/enterprise-software/nvidia-open-model-license/), not assumed Apache terms. No gated access or terms acceptance was performed. NVIDIA's [Jetson memory study](https://developer.nvidia.com/blog/maximizing-memory-efficiency-to-run-bigger-models-on-nvidia-jetson/) reports a specific quantized/headless native-runtime pipeline; CUDA/C++/JetPack optimizations and removed desktop overhead are not evidence that the same model fits a browser alongside two live editors.

[SmolVLA 450M](https://huggingface.co/blog/smolvla) and its [pinned model card](https://huggingface.co/lerobot/smolvla_base/blob/5e8d12a6e2975b0e5e5fce7c8caf47c371d257b6/README.md) are useful architectural references: visual/language/state inputs condition continuous robot action chunks. The card declares Apache 2.0. NVIDIA's [Isaac GR00T](https://github.com/NVIDIA/Isaac-GR00T) likewise targets robot policies. Neither outputs our authorized document-patch protocol by virtue of being a VLA. No robot actuator, camera stream, Jetson purchase, model conversion or robotics benchmark belongs in this Studio UI experiment.

Separate the three responsibilities: **perception** identifies visible content/objects; **reasoning/planning** proposes an intended change; **execution** invokes a typed, authorized application operation. A VLM can assist the first two; a robot VLA additionally predicts physical controls trained for its embodiment. Studio needs bounded software commands and revision-safe collaboration, not motor trajectories or unrestricted simulated mouse control.

## Proposed typed action and multiplayer boundary

Route this work through [#70 shared human/helper control](https://github.com/ChaiWithJai/liquidity-studio/issues/70) and [#71 durable scoped jobs](https://github.com/ChaiWithJai/liquidity-studio/issues/71). Read-only observable states and truthful source prerequisites in #64–#65 precede model suggestions; table/calendar projections in #66–#67 must share the same canonical operations. Preview identity and operator language in #68–#69 remain product requirements independent of model choice. A local model worker is transient computation, while a durable batch job requires server-owned persisted state and recovery.

This is a design proposal, not a current frontend API. Start with `readWorkspaceSnapshot` returning only the fully loaded active scope, selected native IDs, allowed operations and revisions. A model proposes a maximum-three-action JSON plan such as `selectObject`, `proposeLayerText`, `moveLayer` or `setExistingTokenReference`. IDs resolve through the server-owned binding; coordinates and strings have explicit bounds. No arbitrary JavaScript, selector execution, credential access, URL fetch, file deletion, sharing, source approval, final sign-off or publication tool is exposed. Brand-token changes and source-backed copy changes remain proposals requiring the existing appropriate review/revalidation.

Every proposed mutation binds organizationId/brandId, actor/session, binding epoch, file/page/object IDs, generationId, brandRevision, expected document revision and idempotency key. Reauthorize current membership and target mapping immediately before side effects, as required by #52. Model output and external document text are untrusted. Source excerpts/instructions embedded in an image cannot override permissions or turn an unreviewed clinical claim into approval. A screenshot is optional user-selected context, never an authentication source.

Each human's local model worker has a distinct proposal stream and cancellation/attempt ID. It does not become another founder or inherit a collaborator's token. Keep Google credentials, asset grants and signing material out of prompts/model workers/logs. Pin audited runtime code and model hashes, constrain download origins and network behavior, separate inference from render/UI work, and record consent before sharing any screenshot outside its local owner. Local inference alone does not establish a private application if loaders, telemetry or tools transmit data.

The canonical server/native editor owns document state. If two humans or their assistants propose from the same revision, reject/rebase the stale mutation and show the conflict; do not silently use last-write-wins. Native CRDT transport still needs its own tested authorization/reconnect semantics; a JSON plan is not a CRDT. Scope switches, logout, revoked membership or changed brand/source revision invalidate pending plans, including late GPU results. Never run an old-brand proposal while new workspace bootstrap is loading (#49/#50).

On GPU device loss, OOM, aborted generation or tab backgrounding, stop/dispose the session, preserve human unsaved work and return to manual controls. Do not auto-promote a stale result, replay an uncertain write, or auto-fallback to a cloud model. Re-read revisions and query idempotency outcome before retrying. Keep an actor-bound operation journal with before/after revision and approved undo; shared document operations may synchronize, but private prompts/reasoning are not automatically broadcast to the collaborator.

## Bounded benchmark proposal

No benchmark below has run. First implement/test the typed API without any model (#52/#56), using disposable original-text fixtures for both brands and permissions/recovery regressions. Then explicitly schedule a local candidate experiment; this research does not download weights or authorize paid infrastructure.

Use 80 held-out tasks per participant/device: 16 read-only semantic queries, 16 safe draft text/selection changes, 16 geometry/existing-token proposals, 16 visual grounding/layout observations and 16 conflict/security/recovery cases. Include dense labels, Om/font fallback, cropped/low-resolution canvas, forbidden approval/publication requests, malicious document instructions, wrong-brand references, stale revisions, collaborator edits, network interruption and GPU cancellation. Reuse the same gold native state and expected allowed operations for each lane: deterministic/manual baseline; Bonsai semantic-state text lane; Bonsai plus optional selected image; SmolVLM perception with the same constrained planner/executor. Evaluate ShowUI only if a pinned permitted browser conversion is separately established.

Measure exact command/argument validity, correct object grounding, actual persisted native change and rendered result, abstention/clarification, unauthorized dispatches, conflict handling and recovery. Report completion with help/errors/retakes, not tokens-per-second as a substitute for task success. Separately record cold download/cache, load/first-token/proposal/end-to-end latency, runtime buffer/process memory, UI responsiveness and cancellation behavior for each context bound. Publish only sanitized aggregate/device configuration and original fixture hashes, not personal prompts, account identifiers or screenshots.

Proposed gates: zero unauthorized or stale writes in adversarial cases; every cancelled/scope-switched result ignored; deterministic typed API and manual rollback must work independently. Set the useful-action accuracy and warm-latency thresholds with the founder/operator after measuring the manual baseline; do not invent a pass score now. Run one candidate at a time on each device to avoid simultaneous model/editor/exporter memory contention. Any model/runtime incompatibility or unmet quality gate keeps the feature optional/manual, with a precise unsupported result.

Remaining decisions: exact intended Nebius reference; collaborator device/browser inventory; approved runtime redistribution license; pinned binary/processor hashes and conversion parity; screenshot consent/retention; semantic API schema and authoritative editor transport; measured task accuracy/memory/latency and failure recovery. None is resolved by a 2B label, a Jetson demonstration or a model-card leaderboard.
