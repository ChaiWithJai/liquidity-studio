## Exact routes and bounds

All routes require the new explicit managed-only defaultOFF flag `STUDIO_DEFIANT_REMOTE_MCP_ENABLED=true`, a configured private evidence provider and managed Google identity; reject trustedTestMode production wiring. No anonymous evidence fallback.

1. GET `/.well-known/oauth-protected-resource/mcp/defiant-evidence`: exact resource, issuer and scope only; public metadata, no organization, user, token or data.
2. GET `/.well-known/oauth-authorization-server/oauth/defiant-evidence`: exact issuer, authorize/token URLs, code response type, authorization_code and refresh_token grants, S256, evidence:read, token auth method none, issuer identification true. Public metadata does not issue authority.
3. GET `/oauth/defiant-evidence/authorize`: validate exact configured CIMD client, exact allowlisted redirect, resource, scope, response_type=code, bounded state and S256 challenge. Create a short-lived opaque pending authorization transaction; show no evidence. Redirect only to fixed same-origin Studio consent screen carrying the transaction ID, never raw bearer or refresh token. Authorization parameters can be retained server-side; do not trust them when the approval POST returns.
4. POST `/api/studio/remote-evidence/{inspect,approve,deny,list,revoke}`: normal managed Google bearer, existing session/epoch scoped request and current organization access; strict4KiB5s JSON. Approval explicitly displays client, exact organization, evidence:read, target resource and maximum lifetime. Bind pending transaction to selected organization and Google UID only at explicit approval. No auto-consent, hidden account choice or new identity/profile.
5. GET `/oauth/defiant-evidence/complete?transaction=<opaque>`: one-time consume approved/denied transaction and redirect to its already validated exact callback, echo bounded state and exact `iss` on success and valid-client errors. OAuth code is short-lived and appears only in standard callback; no evidence/access/refresh credential in URL. Use no-store and Referrer-Policy:no-referrer on consent/completion responses.
6. POST `/oauth/defiant-evidence/token`: strict8KiB URL-encoded body and5s deadline, reject duplicate/unknown fields; library-backed authorization_code and refresh_token only, no password/client_credentials/implicit grant. Return standard OAuth JSON, no-store/Pragma:no-cache. Verify exact client/resource/redirect/scope/PKCE/code and current authority.
7. POST `/oauth/defiant-evidence/revoke`: bounded RFC7009-style revocation for the calling configured client, idempotent, no token disclosure. Normal Studio remote-client revoke remains available.
8. `/mcp/defiant-evidence`: SDK Streamable HTTP POST plus GET/DELETE/OPTIONS only as required by SDK/stateless transport; a GET may legitimately return405, not a bespoke SSE server. Exact Host and optional Origin allowlist, no cookies as API credentials, no arbitrary CORS reflection, JSON body<=64KiB/5s, request deadline30s, response<=4MiB. Reject malformed prefix/query/path before generic body consumption. SDK bearer gate challenges unauthenticated calls; it never upgrades a Studio session cookie into remote authority.

Initial client mode: CIMD with a strict server-owned allowlist containing only the exact OpenAI client metadata URL displayed in the connection management page. For issuer-identifying stable mode the documented URL is `https://chatgpt.com/oauth/client.json`; callback is `https://chatgpt.com/connector_platform_oauth_redirect`. These remain unconfigured until root actually reads the management values; no guessed callback IDs, wildcard callbacks or automatic substitution. Metadata advertises `client_id_metadata_document_supported:true` and `authorization_response_iss_parameter_supported:true` only when implemented: exact issuer must appear in every authorization success and valid-client error, matching protected-resource authorization_servers exactly. Fetch only the one configured HTTPS CIMD URL, no redirects, JSON<=16KiB/5s and reviewed exact callback match; cache bounded metadata, no arbitrary client-selected URL fetch/SSRF. Token auth method none with mandatory S256 is the narrow public-client choice; do not advertise private_key_jwt unless separately implemented. If management supplies callback-ID-specific metadata, bind that exact client metadata and callback pair instead. A predefined public client is a documented fallback only if actually chosen in host management, not silently mixed with CIMD. DCR is not exposed in this slice. This is one connector configuration, not a new account/RBAC matrix; no client secret is needed.

## Authority, persistence and replay

Use current DurableStore/Firestore adapter, not another database. New namespaced bounded key(s) for remote OAuth transactions/grants keep existing local grants unchanged. Reuse existing managed UID/account revocation and `DefiantStrategyService.raw` checks through an exported authority adapter, not a second identity policy.

- Pending transaction/code lifetime5min, maximum128 pending entries; bound state<=512chars, transaction identifier32randombytes, one-time code32randombytes. Persist code/credential SHA256 hashes only. No source cells or Google tokens in this state.
- Bind code to client ID, exact redirect URI, exact resource, exact scope, S256 challenge, owneruserID, managed UID, chosen organization and approvedAt. Code verifier43..128 unreserved characters, challenge43base64url; reject plain/missing/downgraded parameters. Constant-time comparisons. Failed verifier attempts consume/revoke the code; atomic one-use exchange prevents concurrent replay.
- Remote access opaque distinct family from ea/er;5min lifetime. Refresh opaque distinct family; absolute8h maximum, never extended. Store token hashes, client/resource/scope/grant binding. Return credentials only in HTTPS token responses to ChatGPT, not browser UI/public config/logs. No JWT signing secret/new SecretManager/IAM needed for stateful opaque tokens.
- Rotate refresh and access together atomically; old access invalid after rotation. Retain bounded consumed-refresh tombstone until family expiry; reuse revokes the family. Transport loss requires relinking rather than replaying a consumed credential. No transparent broad-credential fallback.
- Every MCP request verifies token hash/expiry/client/resource/scope and current grant, then current managed UID/account/token-valid-after and organization membership. Every service.read repeats authority before and after provider load/async cells. Revocation, disabled account, changed UID or membership removal returns challenge/denial without private structured payload.
- Tool metadata declares OAuth evidence:read in securitySchemes. Auth failures supply SDK HTTP WWW-Authenticate and tool-level `_meta['mcp/www_authenticate']` where host linking requires it; do not simply convert401 into the current generic503 wrapper. Current stdio generic denial behavior remains unchanged.
- Deterministic pruning on write, hard caps on transactions/grants/tombstones and existing store transactional CAS; no scheduler/TTL service required. No request/response/raw credential logs, only finite redacted audit outcomes.

## Browser transaction cookie binding

Authorize sets `__Host-defiant_oauth=<transaction>.<random-secret>; Path=/; Secure; HttpOnly; SameSite=Lax; Max-Age=300`, with no Domain. Store only the secret hash; reject duplicate cookie names and mismatched transaction/hash. Inspect, approve, deny and completion require this cookie, but managed Google bearer/current authority remain mandatory for consent operations. Cookie alone never approves or authenticates MCP. One browser cookie intentionally makes concurrent authorization tabs fail closed: newest cookie cannot complete an older transaction; explicitly restart it. Clear terminal cookie with identical attributes and Max-Age=0. No access/refresh token enters a URL or this cookie.

## Required review corrections and bootstrap contract

- **Metadata bootstrap:** enabled+managed-provider configured with `allowedClients:[]` is valid. Serve exact protected-resource and issuer metadata without client registration, ADC/provider snapshot reads or data. Authorize/token requests deny unknown/unconfigured clients until root obtains the actual management metadata URL and callback and adds the reviewed exact pair. Disabled feature returns404 for these routes. Never insert a fake callback or guess an identifier to let registration proceed.
- **Client authentication intersection:** resolve the configured CIMD document with strict bounds, then intersect its plural `token_endpoint_auth_methods_supported` with server-supported `[none]`. Accept none when the plural array contains it even if legacy singular `token_endpoint_auth_method` names private_key_jwt. Singular is a compatibility fallback only when plural is absent; malformed/empty/unsupported intersection fails. Never select private_key_jwt without implementation or silently downgrade a client that does not offer none. Preserve configured exact URI strings and compare redirects byte-for-byte; validation does not canonicalize untrusted redirects.
- **Atomic consent:** inspect uses normal Google auth and echoes immutable transaction ID/client/resource plus selected org and current owner UID context. Approve/deny require that exact inspected version/context and are atomic terminal transitions from pending. The first authorized terminal action fixes UID/org/client/resource; a different actor/org cannot replace it, and approve versus deny races cannot both win. Completion consumes only that terminal state. UI captures org/user/session epoch and aborts/discards changed-context replies. Add competing approve/approve, approve/deny, owner-switch and inspect-stale tests, not merely sequential happy paths.
- **Public revocation:** require possession of the exact opaque access or refresh token and matching configured client/family/resource binding. A client_id or grantId alone is never revocation authority. SHA-match before family mutation; unknown token, wrong client/family and already-revoked token return the same success shape/status, reveal no token/grant existence and mutate nothing unrelated. Normal signed-in owner revoke separately checks currentUID/org/ownedgrant.
- **401 versus403:** absent/malformed/expired/replayed token is401invalid_token with metadata challenge; a valid token missing evidence:read is403insufficient_scope. A currently disabled account/changedUID/revoked membership/deniedorganization is403access_denied with no data, not an invented scope deficiency and not silently retried as another identity. Tool read denial after provider load stays403; only an actual401auth requirement triggers host relinking metadata. Finite redacted errors preserve this distinction instead of converting401to503.
- **Limits:** persistent namespace hard caps128pending transactions and64live grant families; cap consumed-code/refresh tombstones4096 until their original expiry. Prune expired entries only. Full state or tombstone capacity denies new authorization/rotation before consuming another live token; never evict live grants/tombstones. Authorize starts maximum30/minute global, approval/denial5attempts/transaction, token exchanges/refresh120/minute global and10/minute/client-family, revoke120/minute global. Bound attempted counter updates transactionally; use fixed validated client/family digests, not arbitrary unbounded input keys. Transient per-process ingress limits are supplemental only. Tests cover caps and unchanged live/tombstone state under rejection.

## Engine transaction adapter and exact dependency plan

Read exact5.3.0 upstream code, not only current docs. `AuthorizationCodeGrantType.handle` invokes getAuthorizationCode then revokeAuthorizationCode BEFORE PKCE verification and saveToken. The adapter must perform atomic compare-and-consume in revokeAuthorizationCode and return false to the losing contender; getAuthorizationCode is not authority to issue. Failed PKCE consumes the code as upstream intends. `RefreshTokenGrantType.handle` similarly loads then revokeToken before saveToken; use alwaysIssueNewRefreshToken=true and atomic family version/hash claim. Each token request owns a fresh model/context instance so callback state cannot cross concurrent requests. Model saveToken must recheck the claimed transaction/family version, current authority and original absolute expiry before atomic persistence of BOTH new token hashes. Claim followed by save is intentionally two transactional phases: a crash/write failure after consumption fails closed and requires relinking, never restores an old credential. No misleading claim that the library's whole callback sequence is one database transaction.

Library guards are additive to adapter exact resource/client/redirect/S256 validation. Override token/code generation with32randombytes and only persist hashes. Inspect exact authorize/saveAuthorizationCode model requirements before implementing, and test durable compare-and-consume with concurrent actual engine calls. Refresh replay detection revokes its own family through retained hash tombstones; stale invalid claims cannot save a successor. No background cleanup architecture is introduced.

Its exact tagged package declares @node-oauth/formats1.0.0, basic-auth2.0.1, type-is2.0.1; hosted lock-only resolution must pin actual complete transitive integrity closure and compare every pre-existing lock entry/version/resolved/integrity, with no removals/unrelated upgrades. Do not handwrite integrity fields. Root coordinates ONE existing-SA/bucket hosted lock-only job after review; package scripts ignored, no application build/models/runtime in that job.
