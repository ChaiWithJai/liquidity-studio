# Registered hypotheses and evidence-linked outcomes

Status: owner-authorized next evaluation slice; specification for independent review before code. Based on accepted356 source067c499; merged-main ancestry will be integrated before implementation publication. No source, model execution, migration, runtime activation or prospective experiment is claimed by this document. Follow the retained Addy specify→plan→tasks workflow under existing owner authorization.

## Problem and objective

Historical B1–B5 expectations have a shared baseline timestamp and prior pilot knowledge, but no immutable per-hypothesis criteria or machine-linked outcomes. Preserve that history. Existing answer observations require an already supplied answer and assertions; creating a fabricated answer to register a hypothesis would corrupt their meaning.

Add a real Studio vertical slice: explicitly register a frozen hypothesis against a resolved baseline; reload it; explicitly link a later fact or a saved answer assertion; read the exact numerical result and its temporal limitations; optionally append one attributed correction. Keep the existing17 evidence MCP tools read-only and unchanged. This supplies auditable registration and result order, not prediction accuracy, causal effectiveness, independent human truth or commercial activation.

## Capability and first-slice boundary

Reuse the existing private observation domain, DurableStore, current Google authority, strategy.assertCurrent and finite evidence service. Use a separate versioned hypothesis record schema rather than modifying old answer records. No new database, scheduler, public endpoint, GCS lookup, model call, arbitrary formula or campaign training export.

First machine-evaluable metric: `source-total-earned`, exact signed decimal amount in one currency for one explicitly selected earnings month. The service already returns this metric with sourceHash and a month+currency selector. Selection aggregates lack a verified period: they are deliberately not accepted as first-slice business-outcome selectors. Later comparison, selection and audience criteria need their own meaningful semantics and remain in the broader evaluation scope.

Two distinct outcome types:
- `evidence-fact`: read the registration-frozen earnings month+currency at a supplied current revision.
- `answer-assertion`: link one existing saved answer observation and an assertion index0–4. This checks the frozen source fact behind that assertion; it does not turn answer text or the assertion's equality check into a business result. Preserve observationID, answerHash, evidenceRevision, createdAt and attributed metadata.

## Registration contract and immutable baseline

Exact request fields: idempotencyKey, mode, question, expectation, priorKnowledge, baseline, target, criterion, supersedesHypothesisId.
- mode is analysis-expectation|future-period-outcome. priorKnowledge is required attributed text<=2048UTF8bytes describing already inspected evidence/pilot knowledge; it is not a verified blindness attestation. Baseline evidence is explicitly known at registration.
- question and expectation are required attributed text, each<=2048UTF8bytes. Never label them generated/model-verified.
- baseline exact fields: revision (64hex), month (YYYY-MM), currency (3uppercase ASCII letters). Resolve `earnings` with month,currency,limit1,revision under current scope; require exactly one item and exact returned org/revision. Registration rejects a missing baseline (404 baseline-missing), ambiguous total>1 (409 baseline-ambiguous), or missing/unsupported metric (409 baseline-metric-unsupported); it does not persist an unresolved baseline or invent zero. Provider/validation failure remains503, not absence.
- Freeze resolved amount, currency, metric, month, sourceHash, source qualification and exact revision. Only `source-total-earned` accepted. Freeze baselineHash over the canonical resolved structure and criterionHash over the canonical criterion/target.
- target is exactly {month:YYYY-MM,currency,metric}; currency and metric must match the resolved baseline. Freeze this finite logical target at registration; later linking cannot choose another month/currency after seeing results. Validate a real YYYY-MM calendar month in the finite supported year range1900–9999, then derive calendar start inclusive/end exclusive UTC (reject an unrepresentable end). analysis-expectation permits historical business periods: registering before a later analysis capture is distinct from forecasting that business period. future-period-outcome requires start after registration and baseline month before target month. No caller registration timestamps/backdating. Neither mode proves unseen evidence; source availability remains unknown.
- criterion exact fields: metric=`source-total-earned`, currency identical to baseline, operator in lt|lte|eq|gte|gt, threshold exact signed decimal string (same26integer/12fraction bounds as observations). It compares the later absolute amount, not a delta, ROI, forecast or causal response. No float arithmetic.
- supersedesHypothesisId nullable64hex. If supplied, require an existing hypothesis in the same org, reject equality with the newly derived ID, and freeze the link; do not mutate its expectation/criteria. A new registration has a new server time and the selected mode's temporal rules.

Server freezes schemaVersion1,evaluatorVersion=`absolute-source-total-earned-v1`,baselineAdapter=`createDefiantEvidenceService`,baselineSchemaVersion from the actual response (currently1; reject unsupported values),hypothesisId,organizationId,registeredAt,actorId,actorUid,question/expectation and their hashes,baseline,criterion,target,mode,priorKnowledge,temporalQualification (mode-specific; source-availability-unverified),supersedes link. Original fields never change. There is no supplied boolean capable of granting prospective status.

## Outcome link and evaluation

Exact request: idempotencyKey, kind, reference, observedAt. observedAt nullable canonicalISO time is attributed/unverified, never substitutes for server recordedAt.
- evidence-fact reference exactly {revision}; month/currency/metric come from the frozen target, never from the outcome request. Resolve the same finite earnings lookup, exact org/revision, unique item or explicitly unknown if absent. Persist returned fact/sourceHash/metric/qualification; no request path/hash lookup.
- answer-assertion reference exactly {observationId,assertionIndex}. Transactionally validate same-org immutable observation existence. Freeze only its selected bounded result, source fact, declared assertion, period qualification and metadata; retain answerHash rather than copying the whole answer. Reject selections for this first contract because their period is unknown. No fabricated answer or rewriting that observation.
- Capture may record an incompatible/missing fact as an explicit diagnostic result, but numerical evaluation is `unavailable` with a finite reason from evidence-missing|evidence-ambiguous|metric-incompatible|currency-incompatible|period-incompatible|period-not-elapsed|business-series-unverified. Missing total0 differs from ambiguous total>1. A provider error does not become evidence-missing and must fail the operation without a saved verdict. No matching by title/file name. The frozen target remains unchanged even when a linked assertion is incompatible. Same revision/source fact is labeled reused-known-evidence, never new or independent outcome evidence.
- In analysis-expectation mode, compatible facts yield only `criterion-met` or `criterion-not-met` using exact scaled BigInt comparison, with `evaluationMeaning=declared-analysis-numeric-rule`. This is not a supported forecast or independent validation. Preserve sourceHash change/reuse and whether the revision changed; a newly uploaded hash is not verified new knowledge. Server registration precedes result capture only; actual analysis execution/source availability remain unverified.
- In future-period-outcome mode, first-slice business evaluation remains `unavailable` unless stable business-series identity and source-period completeness can be verified. Current earnings product exposes only declared month,currency,metric,sourceHash; org membership is not a catalog/account identity mapping. Therefore this slice can register such hypotheses and retain later evidence, but cannot yet certify their business outcomes. Period-not-elapsed is an additional unavailable reason. Do not substitute source hash equality, upload time or attributed observedAt for missing identity/availability evidence.
- An answer-assertion link additionally reports `outcomeMeaning=answer-assertion-evidence`, never a business-outcome label. Observation capture before registration is explicitly historical/retrospective linkage; its compatible numerical check may be shown only as retrospective analysis, never prospective evaluation. Observation capture after registration establishes record order, not independently verified model/analysis execution time.

Each hypothesis accepts one immutable linked outcome in this bounded slice. A wrong link cannot be silently replaced: append one correction {idempotencyKey,comment} with comment<=2048UTF8bytes, separately attributed to current actor/UID/server time. Correction does not change facts, criterion or verdict. Re-run/revised expectations require a new hypothesis with supersedes link, preserving the historical chain. One correction slot applies to the whole hypothesis/outcome record and is only available after an outcome exists.

## Persistence, authority and replay

Use keys `defiant-evidence-hypotheses:v1:<org>:index` and `...:<hypothesisId>` alongside existing observations, not campaign telemetry. Index<=100 lightweight entries/org; each complete record<=64KiB including outcome/correction, input<=16KiB, list bounded100 with no source cells. Capacity rejects without eviction. These per-record limits do not guarantee the total identity/strategy transaction size; retain the existing4MiB aggregate guard and fail before writes when exceeded.

Registration ID is SHA256(org,actorID,UID,idempotencyKey); payload hashes use validated canonical field ordering. Same key+same payload returns the current envelope containing the original immutable registration fields after maintained authority (even if an outcome/correction was subsequently appended), without requiring the old evidence provider still available; changed payload409. Precompute IDs/hashes before retryable callbacks. Freeze registeredAt only after baseline resolution and maintained authority, immediately before transaction preparation; this is a server-record timestamp, not proof of physical commit time. Future-mode target start is checked against a fresh server clock before commit and inside each callback retry; crossing the boundary rejects without regenerating candidate time/ID. Outcome has separate idempotencyKey/payloadHash stored with its immutable result; same key+payload replays, conflicting payload or second outcome409. Correction also stores its canonical payload hash/key: exact replay returns the original correction, changed payload or different second correction409. No new timestamp on replay.

Async evidence reads occur before the final transaction. Reauthenticate maintained Google identity with exact actor/UID and strategy.raw before work and immediately before commit. Transaction callbacks are synchronous and only check strategy.assertCurrent against current identity+strategy state and mutate bounded documents. Registration uses identity+strategy+index+record and optional superseded-record key (5). Outcome uses identity+strategy+hypothesis and optionally observation record (4); reread immutable linked observation inside that transaction and compare its retained payload/answer/evidence identity. No external side effects in callbacks, no callback timestamps/IDs changing on retries. Concurrent submissions must converge to one record/result.

Existing-record replay/list/detail/correction are equally authority guarded. Abort/deadline checks precede and run inside callbacks; timeout can race a remote commit. Retain same key and unchanged request for readback, never promise rollback. External Firebase revocation is not atomic with persistence. Local ea/er and remote OAuth read grants cannot read or write this private registration domain.

## HTTP and actual UI

Under existing `/api/studio/defiant-evidence/:org/hypotheses`: GET list, POST register; `/:id` GET detail; `/:id/outcome` POST link; `/:id/correction` POST comment. Exact route/method/body schemas; no query parameters. Managed Google only, current org strategy and configured evidence provider required. Explicit16KiB body/5second read guard and30second operation deadline. Do not loosen general Studio or MCP authorization.

Add an explicit Evidence explorer panel alongside Answer observations. Registration form exposes baseline month/currency/revision, question/expectation, mode, prior knowledge, frozen target month, operator and threshold. Resolved baseline shown from returned server record; no client calculation. Saved list/detail survives reload. Outcome form explicitly selects evidence fact or saved observation+assertion. Show each finite evaluation-unavailable reason and temporal/evidence-reuse qualification alongside the numeric rule result; never display a blanket success/verified badge; escaped text, ordinary source links using existing finite explorer URLs, no hidden scans. Show original registration and linked result immutably with one correction. Account/org/revision context fences and pending-request cancellation follow existing observation UI; no automatic registration/linking.

## Acceptance and preserved scope

Complete implementation requires persistence+explicit UI+readback, not a throwaway validator. Acceptance must prove scopes, replay/concurrency, immutable baseline/criteria, null-vs-zero, exact currencies/metrics/window, incompatible result unavailable, historical answer never prospectively upgraded, escaped/stale UI and honest corrections. This slice does not complete the broader five questions, classifier evaluation, same-question before/after model experiment, consented human practice, rights or actionable gold outcomes. A later model experiment separately freezes actual question/prompt/model/config and answer pairs with declared confounders and independent labels; these records alone supply no inference-improvement score.
