# First Cloud Run pilot service versus later revisions

The installed Google Cloud SDK 558.0.0 rejects `--no-traffic` when creating a service. Its `googlecloudsdk/command_lib/run/config_changes.py`, `NoTrafficChange.Adjust`, raises `--no-traffic not supported when creating a new service.` A deployment cannot use a previous serving revision until that service exists. See the [gcloud deployment flags](https://docs.cloud.google.com/sdk/gcloud/reference/run/deploy) and [traffic migration guide](https://docs.cloud.google.com/run/docs/rollouts-rollbacks-traffic-migration).

The unconditional flag was introduced in [`401ca78`](https://github.com/ChaiWithJai/liquidity-studio/commit/401ca78), the first pilot deployment script. It is valid for staging a new revision of an existing service, but blocks the initial service under #19. No production deployment failure is claimed: the current read-only audit found no service in the pilot's region before this repair.

`scripts/gcp-pilot.mjs` now requires a successful authoritative `gcloud run services list` in the explicit project and `us-east4`, with a JSON metadata-name projection. Invalid JSON, unknown record shapes, duplicate names and every unsuccessful command fail before deployment. An error containing `NOT_FOUND` is not evidence of absence; only a valid successful list without the target service establishes absence.

- Existing service: retain `--no-traffic`. Main service traffic stays with the existing revision. The `pilot-candidate` tagged URL can still receive requests and incur costs; zero assigned main traffic does not mean no network access.
- First service: omit the unsupported flag and report **100% initial traffic**. Public surfaces support Google sign-in/static assets (including necessary public configuration and health); studio/admin data APIs require verified Google identity, role and membership. This is an initial authenticated pilot deployment, not a zero-traffic candidate. The URL is reachable immediately after creation; validate it before inviting users. There is no previous serving revision for revision-based rollback on this first launch.

This does not weaken the immutable-image acceptance report, Google-mode/anonymous-denial evidence, explicit project/region/billing budget checks, provider verification, private Firestore/GCS guards, runtime identity, single-instance limit, inference bounds, clear-secret mounts or rollback checks. First service selection is a read-before-deploy decision; serialize operator deployments to avoid a competing deployment changing service existence between that check and the CLI mutation.

After a first deployment, capture actual service/revision URLs and traffic, configure the intended Cloud Run hostnames as Firebase authorized domains where needed, then verify both Google users, outsider/anonymous API denial, scoped editing and actual downloads, runtime storage/Vertex access and recovery. Later revisions can use normal no-traffic staging. No cloud mutation or paid inference was performed to test this change: tests intercept gcloud/provider boundaries, including first/existing services, lookup failures, malformed responses and existing evidence/budget/provider/storage rejection paths.

The aggregate USD100 alert budget remains an alert budget. This change neither creates service spend caps nor implies a hard all-service spending ceiling. Keep current attempt/input/output and instance controls and evaluate optional eligible-service caps separately.
