# Reviewed Penpot backend candidate artifact

This manual hosted workflow produces a downloadable candidate, not a deployment. It leaves the existing verification workflow unchanged and requires a completed successful `penpot-native-hook-verification.yml` run with its unexpired evidence. It does not rerun those tests.

Dispatch `penpot-backend-candidate-artifact.yml` with the full reviewed Studio `source_sha`, successful `verification_run`, and confirmation `build-reviewed-penpot-backend-candidate`. A frontend/docs-only later commit is accepted only when the complete four native-tool directory inventories and every byte match the successful verification, and all three verification recipe files match its immutable recipe Git blobs. Both source identities are retained. Run39148079704 verified d825cd2e4640f1471153cd48cf89116b44071fae; it is a possible input only if these checks still pass, not a hardcoded approval.

The first hosted job checks out upstream `ff7a66f51938b2293260ea27a64e2c4e0833b5e3`, applies the reviewed exact-source hooks, then calls the pinned upstream `clojure -T:build jar` under the same official Java27 toolchain. It uses the production dependency basis, preserves2.18.3 version/changelog resources, includes the pinned common Java classes, and checks packaged backend source bytes. It avoids the upstream full bundle script's remote onboarding-template prefetch. Dependencies and lock files are unchanged.

The second job requires a native `ubuntu-24.04-arm` hosted runner. It pulls only `penpotapp/backend@sha256:2df1b3440d2a82cc3571db211b4ffdfa2b89ccc910759e8d5e9387fb62971b5c`, checks linux/arm64, then makes a jar-only derivative. That is the registry digest of the actual maintained2.18.3 ARM64 backend. Its JRE is26.0.2; the workflow checks the actual JRE before loading `app.main` and all integrated hooks under Java26, without calling main/Integrant, any database, or listener. Configuration is unset and network is none. This runtime compatibility check is required because the earlier verification toolchain is Java27 AMD64.

Artifacts contain the JAR, image tar, applied source correspondence with upstream MPL license/changelog, dependency declarations, source/JAR/image hashes, source/recipe/run provenance, logs and explicit acceptance limits. The image inherits official user, command, templates, native tools and JRE. No private native configuration, credential or cookie is read or packaged. No image is pushed; no service, database or native policy is activated. Existing native runtime is untouched.

Resource bounds: JAR job8GiB/no swap/4CPU with25minute container deadline; ARM compatibility check1536MiB/no swap/2CPU with180second deadline; namespace JVM heap1024MiB. Image assembly120seconds, image save180seconds, exported compressed image≤2GiB. These are hosted build/smoke budgets, not customer runtime capacity claims. Missing ARM runner, expired evidence, mismatched inputs, unavailable pinned image, incompatible Java26 load or any failed step stops delivery. There is no alternate image/version/architecture fallback.

Actual isolated candidate startup and founder/Nicole same-design edit/reopen, fonts/images, private-sharing and five-second revocation acceptance remain separate required operations. Compilation, module versions and artifact creation do not prove those behaviors. The current candidate has not yet been built or run.

Artifact inspection distinguishes the standard `data_readers.clj` resource from application source: tools.build merges reader maps from dependencies. All ordinary backend sources must remain byte-identical. For this one resource, a bounded hosted `clojure.edn` read of the original and actual JAR entry requires symbol→symbol maps, rejects tags/trailing forms, and checks every original mapping is unchanged. No reader symbol is resolved or invoked. Both resource hashes, map counts and preservation result are recorded; failure stops the build.
